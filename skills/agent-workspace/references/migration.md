# Migration and recovery

Use for migration, cleanup, and substantial initialization edits. Audit and validation apply no transformation.

1. **Assess the whole directory.** Resolve the selected path and affected ancestors; identify governing scope, owners, privacy/export rules, symlinks, nested repositories and unrelated work. Inspect structure including hidden locations, legacy `files/` and `scratch/`, and nested operational bundles. Sample sufficient content to classify each candidate group; expand around mixed purposes, uncertainty and dependencies. Avoid indiscriminate loading of source libraries, generated dependencies or sensitive recovery payloads. A folder name never establishes an exemption. References and historical approvals do not authorize external edits or backlog execution.
2. **Map coverage and meaning.** Account for every candidate group as moved, split, consolidated, retained with justification, excluded by an explicit boundary, or unresolved. For each transformation, map useful instructions, knowledge, provenance and workflows to authoritative owners, and identify consumers needing path repairs. Use [purpose-based layout](layout.md#purpose-and-discovery). An edited-file list alone is not coverage. Resolve contradictions from evidence or report the blocked choice. Migration permits disruptive organizational changes, including replacement of obsolete catch-all placement/routing rules; preserve substantive domain/safety meaning unless separately grounded/approved.
3. **Protect originals.** Before destructive rewriting or removal, identify an exact recoverable version of every affected original, including uncommitted bytes. Verify copies by bytes or hashes; a committed version suffices only if it matches. Choose private recovery outside auto-loaded/published paths, checking existing exclusions and protections. Protect only what the planned changes require; intact moves or exact existing versions do not automatically require whole-workspace duplication. Define temporary recovery's closeout condition before creating it; no particular directory name is required. If no safe recovery is available, leave destructive portions unapplied and report the gap. Record source-to-backup mapping and restoration method privately; preserve permissions and restoration references. Recovery payloads need not be loaded to assess their purpose.
4. **Restructure and consolidate.** Freshly reread before narrow edits; preserve intervening work. Move appropriate agent records/artifacts into `.agents/` with genuine nested ownership. Split mixed content by purpose; select files versus directories from retrieval needs. Extract durable knowledge, reconcile demonstrably superseded summaries against evidence, and separate current task state from useful dated execution history. Preserve unique sources, actual deliverables and unrelated content. Retaining an archive of every redundant version is unnecessary.
5. **Repair dependencies and discovery.** Check working environments, scripts and recovery bundles for path assumptions, permissions, symlinks and restoration relationships before moving; verify them afterward. Repair routine in-scope paths and consumers, anchors and conditional routes. Route useful internal groups through an established index/task/topic without bulk loading. If relocation requires tool installation, uncertain reconstruction or unrelated infrastructure changes, mark the group blocked or retained with its reason. Report external consumers without changing their owners. Repair legacy routing rather than retaining blanket aliases; any necessary alias needs a demonstrated consumer and removal condition. Apply the checkout rules below before moving any repository.
6. **Remove only verified superseded records.** First verify useful meaning has an owner, references are repaired and recovery works. Age, similarity or scratch placement alone do not justify deletion. Keep unique history and sources; do not delete a container with unrelated content.
7. **Verify, close out and report separately.** Review coverage/dispositions, semantic preservation and mechanical correctness using [validation](validation.md). Unresolved groups prevent claiming their portion complete even if edited-file checks pass. Test recovery in a disposable location, without overwriting the current workspace, then apply [temporary-artifact closeout](#temporary-migration-artifacts). Report changed paths, actual checks, Git changes, blockers/exclusions and any recovery retained with its reason and exit condition.

## Temporary migration artifacts

Distinguish temporary material created for this operation from operational backups, useful evidence, original sources/history and unrelated user data. A hidden directory, old date or backup-like name does not establish disposability. Use an existing protected location where appropriate; do not scaffold a permanent target-local recovery directory by default.

Keep verified recovery available through the destructive work and its validation. After the selected scope passes coverage, semantic-preservation and mechanical checks, repair references and remove this operation's temporary rollback copies, disposable restore-test trees, intermediates and empty containers unless there is a specific reason to retain them. Confirm they contain no unique knowledge/source material, unresolved work or live dependency before removal. Useful concise verification evidence may remain at its private owner; it is not automatically a temporary artifact.

Retain temporary recovery only for an explicit user/project retention rule or a concrete unresolved rollback need. Record its purpose, protected location and removal event or condition; retain only the affected portion needed. A general desire to keep every option open is not a retention policy. Do not relocate or re-archive a disposable copy merely to preserve it after its purpose is fulfilled.

This closeout belongs to the requested mutating operation and needs no separate Cleanup invocation. It does not authorize purging pre-existing recovery, operational backups, original history or evidence from other operations. If validation fails or preservation is uncertain, keep the necessary recovery and report that scope incomplete. Read-only modes never perform this cleanup. Migration completion preserves useful meaning and current operation; discarding temporary originals gives up byte-exact rollback, not permission to discard unique information.

## Intact checkout relocation

Nested repository internals, external symlink destinations and sibling projects are separate boundaries requiring explicit inclusion before internal modification. Selecting a repository as the actual target permits migration of its own agent resources under the Git safeguards below.

A nested checkout may move intact within the selected workspace when its purpose warrants it; do not automatically place product/source repositories under `.agents/`. Preserve the entire directory, including Git administrative data, tracked/untracked/ignored files, dirty/staged work, permissions and internal structure. Inspect location dependencies before and after: Git metadata pointers, linked worktrees/submodules, symlinks, path-bound consumers and relevant external relationships. Verify Git operation and unchanged state when Git inspection is available. If preservation cannot be established, retain/report that group rather than guessing.

Do not reorganize Git administration independently or repair repository internals under parent migration authority. If relocation would require internal Git repairs or out-of-scope consumer changes, report the blocker and leave the checkout operational at its original location. An intact move is not permission to migrate its internal resources.

## Git and concurrent work

Git is optional. When present, inspect status, staged/untracked changes, and relevant tracking/exclusion rules before and after. Preserve the Git index and unrelated dirty files. Moves may appear as unstaged deletions/new files; report them. Migration alone never authorizes staging, committing, pushing, changing ignore/tracking rules, remotes, or global configuration. If a move risks exporting previously private content, preserve the privacy boundary and stop that portion unless the required exclusion change is separately authorized.

Coordinate known overlapping writers when possible. If a contested edit cannot be reconciled, leave it unapplied and report the unsaved proposal in the conversation or an existing project-prescribed conflict location. Shared files do not provide race-free writes; no mandatory queue or locking service is needed.
