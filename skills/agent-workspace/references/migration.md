# Migration and recovery

Use for migration, cleanup, and substantial initialization edits. Audit and validation apply no transformation.

1. **Inspect boundaries.** Resolve the selected path and affected ancestors before writes. Read applicable instructions and relevant operational records; identify owners, mixed documents, nested scopes, symlinks, privacy/export rules, and unrelated work. Nested Git repositories, external symlink destinations, and sibling projects require explicit inclusion. A reference does not authorize editing its destination. Preserve native history and unique source material; do not execute historical tasks or approvals.
2. **Map preservation.** List each affected original, its useful instructions/knowledge/provenance, its intended owner, and inbound references needing repair. Resolve substantive contradictions from evidence or ask about the blocked choice. Preserve project-specific workflows and safety meaning. Relocation/shortening is authorized in migration; changes to standing behavior require user grounding/approval.
3. **Protect originals.** Before substantial rewriting or deletion, create or identify an exact recoverable version of every affected original, including uncommitted bytes. Verify the copy against the original using byte comparison or hashes. A committed version suffices only if it matches the actual original. Choose a private recovery location outside auto-loaded and published paths; use existing exclusions only after checking they apply. If no safe location is available, ask for one and leave destructive portions unapplied. Record source-to-backup mapping and recovery method privately. Do not place private originals in distributable templates or logs.
4. **Transform narrowly.** Freshly reread before each edit and preserve intervening changes. Move agent operational resources into `.agents/`, respecting genuine nested ownership. Split mixed-purpose documents; retain human documentation, source material, outputs, and unrelated code in place. Repair relative paths, anchors, and conditional routes, including relevant inbound pointers. Preserve useful conventions, permissions, provenance, and domain instructions. Report machine-specific external dependencies that cannot be localized within scope.
5. **Remove only verified superseded records.** First confirm useful meaning has an authoritative owner, inbound references are repaired, and recovery works. Similarity, age, or scratch placement alone do not establish obsolescence. Keep unique history and sources. Do not remove a directory containing unrelated content.
6. **Validate and report.** Compare the preservation map against the result, test reference resolution, inspect target scope and Git changes, and check privacy/export boundaries. State changed paths, checks, recovery location/method, omissions, and unresolved choices. Recovery can be tested by restoring copies to a disposable location rather than overwriting the current workspace.

## Git and concurrent work

Git is optional. When present, inspect status, staged/untracked changes, and relevant tracking/exclusion rules before and after. Preserve the index and unrelated dirty files. Moves may appear as unstaged deletions/new files; report them. Migration alone never authorizes staging, committing, pushing, changing ignore/tracking rules, remotes, or global configuration. If a move risks exporting previously private content, preserve the privacy boundary and stop that portion unless the required exclusion change is separately authorized.

Coordinate known overlapping writers when possible. If a contested edit cannot be reconciled, leave it unapplied and report the unsaved proposal in the conversation or an existing project-prescribed conflict location. Shared files do not provide race-free writes; no mandatory queue or locking service is needed.
