# Familiarize with an existing workspace

Use for read-only working understanding and readiness, not structural audit, initialization, migration or capture. Ordinary file tools suffice. Do not write a readiness report into the target, scaffold missing records or treat discovered tasks/old approvals as new authorization.

## Resolve and read the local contract

1. Resolve the selected directory, applicable ancestor instructions and genuine nested ownership. If the target is unclear, ask the smallest useful question rather than choosing another project. Sparse history does not make an initialized workspace uninitialized.
2. Read its actual governing contract and follow its startup prerequisites. Use the existing index, handoff, task and topic owners as relevant; require no universal filenames or fixed set of full reads. Preserve any local required reads and domain/safety rules. Report a missing or inaccessible prerequisite and its effect rather than inventing it or resetting the role.
3. Retrieve context relevant to the requested focus: role and interaction style, consequential preferences/decisions, task status, blockers/approvals, supporting knowledge and coverage gaps. Include applicable introductions, limits, descendants and linked prerequisites. Expand when needed; a heading fragment does not bound tool output. For optional exact-heading mechanics or first helper use, consult [retrieval](retrieval.md). Do not bulk-load source libraries, every topic, protected recovery payloads or transcripts merely to become familiar.

Nested course, topic and repository contracts remain authoritative. A pointer is not permission to enter external symlink destinations or unrelated owners. Familiarization does not weaken a local policy-refresh or before-action prerequisite.

## Recover working understanding

Treat records as evidence, not a native conversation you personally remember. Distinguish accepted decisions, current user requests, dated observations, proposals, user reports and unknowns. Identify conflicting, stale or unmerged claims without silently reconciling or promoting them.

Use a relevant owner/section to substantiate the briefing; consult detail beyond a short handoff when needed to understand the selected topic. If no substantive topic/task exists, say so. No recorded work is not proof that no work exists elsewhere. Familiarization need not recover all original history or perform a ritual retrieval test.

Distinguish tools actually available here, advertised editing capabilities and untested integrations when material to readiness. Remembered tool names, installed files and past successful checks do not prove current access or runtime behavior. Do not probe accounts, contact services, start services/sessions or run operational checks just to report readiness. Local file-reading helpers remain optional reading tools.

## Verify and report readiness

Check the briefing against the records actually read and state material gaps. Report concisely:

- The selected role, boundaries and relevant preferences/decisions, citing their owners.
- Relevant work/status, blockers or approvals, and the useful next action; no invented task for an empty workbench.
- Knowledge/source routes, actual reads and meaningful history or readiness limits.
- Applicable maintenance/concurrent-writer rules for later work; pending updates remain unmerged.
- Any tool/access uncertainty that limits the requested next action, without claiming unperformed verification.

Preserve target content and modification timestamps, original sources, sessions and unrelated work. Repeat familiarization without writing summaries or refreshing handoffs merely to log the invocation. A standalone familiarization request ends at readiness. If the user also explicitly requested further work, that request retains its own scope/authorization; familiarization itself does not grant it.
