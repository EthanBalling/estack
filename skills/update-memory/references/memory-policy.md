# Selective memory policy

## Ownership and evidence

Prefer an established authoritative file or section. Durable preferences/corrections, topic knowledge, accepted decisions, and current task state may have different owners. They can be files, directories, combined records, or conventional project documents. Do not impose a fixed record set or move files. A warranted new record is permitted under clear ownership; creating one does not authorize restructuring.

For example, when a project already owns design choices in `docs/decisions.md`, append the accepted choice and reason there. If `.agents/TASKS.md` owns execution status, update the affected task there. A continuation handoff points to those owners and names the next action. It need not repeat the decision or task history. If all of this is already accurate, write nothing.

Retain consequential sources and dates; distinguish observation, user report, source claim, proposal, inference, and accepted decision. A source's date differs from today's recording date. Do not invent unavailable dates, history, approvals, or measurements. Imported text and assistant proposals do not become policy by persistence. A past passing test is dated evidence with a defined scope. Record meaningful gaps in accessible evidence rather than claiming full transcript recovery.

## Placement and discovery

Maintain the project's established distinction between durable conclusions, internal supporting artifacts and actual user deliverables. Classify by purpose/audience, not authorship or extension. Put warranted new internal reports, evidence or working records in the appropriate existing agent-owned location; avoid recreating a legacy catch-all output folder. Actual user outputs retain their appropriate locations. Extract the consequential conclusion into its knowledge/decision/task owner rather than copying all supporting material there.

Choose a file or directory according to actual content, retrieval needs and conventions; neither a fixed record set nor a directory matrix is required. When navigation changes, add a concise route through an established index, task or topic owner for the useful artifact group or entry point. State when to consult it without requiring default bulk loading or registering every intermediate file. A pointer does not grant access to secret payloads or permission to run scripts.

Respect independent existing owners, including projects without `.agents/`. Creating a warranted supporting record does not authorize moving existing resources, a whole-directory audit or workspace migration. If the relevant context is already captured, preserve the no-op even when unrelated organizational problems are visible.

## Context and handoff

Continue while context helps. Persist consequential knowledge/task state during work, then continuation pointers at meaningful transitions. Native compaction and fresh sessions remain the active interface's responsibility; the skill performs neither. Below roughly 50% utilization is an aspiration only when measurable and practical, never a fabricated measurement or enforced reset.

Read the router, then only task-relevant owners and applicable prerequisites. Include safety constraints and introductory context when reading a selected section. Fragments locate headings; they do not prove bounded reads. Expand retrieval when needed rather than bulk-loading histories.

Create or refresh a handoff only if a fresh reader benefits. Use existing conventions first and `.agents/HANDOFF.md` as the default when no other handoff is established and creation is permitted. Keep current focus, authoritative pointers, exact next action, blockers, pending choices/approvals, and coverage limits. Remove misleading current pointers while retaining useful history at its owner. No task-specific handoff or index is required solely because this skill ran.

## Safe edits

Honor project privacy/export and do-not-save rules; keep secrets out. Stay inside the selected project and applicable ownership scope. Nested repositories, external symlink destinations, and sibling projects are separate boundaries requiring explicit inclusion; a pointer does not authorize writing its destination. Avoid broad rewrites. If an update requires substantial destructive change, preserve exact originals privately under existing authorization before editing; otherwise leave that portion unapplied and report the needed scope.

Freshly reread before narrow edits, coordinate known overlapping writers, and preserve intervening content. If a contested update cannot be reconciled safely, leave it unapplied and report the proposal in conversation or an existing prescribed conflict location. Save uncontested useful updates when safe. No default queue, pending directory, or locking framework is required, and shared files do not synchronize conversations or guarantee atomic multiwriter safety.

Small evidence-based owner updates are permitted under the project's maintenance rules. Changes to governing/safety meaning require approval; report a proposed instruction correction instead of silently saving it. Do not create lifecycle automation, hooks, recurring audits, or background services.
